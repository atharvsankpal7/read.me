While reading a legacy codebase, I found an interesting pattern for handling an empty list for a requested query on filters.

If the frontend requests a list of items with specific filters and the database has no items, then the backend was sending a 404 Not Found error. On the intuition sense this seems correct, but semantically how correct is it?

#What each status code means

It all boils down to the HTTP standards for sending the response. Every response code depicts a state in the system:

  • 2xx means the request-response lifecycle was correctly completed.
  • 3xx means it was completed correctly but with some changes that the client didn't know but the server did, like redirection.
  • 4xx means the client side did some mistake while making the request, let it be trying to access the wrong entity or sending an invalid request body for the server to process it correctly.
  • 5xx is for something going wrong at the server side, like 503 meaning that the server doesn't have enough resources to process the request.

#So what is going on?

So in the above case, what is going on? The frontend did send the correct request headers, was authenticated and was accessing the correct set of entities. So there is no need to send 4xx errors, including 404, since the client is not asking for a specific entity with a unique identifier like a UUID for the backend to say that entity is not found. The client is asking for a list of entities that have certain properties.

Still, the backend was sending the 404 status code, and the frontend was handling that error as a valid response by doing some glue code on the frontend, rendering the empty list message on hitting that status code for that given component.

Important

The handling of the API errors should happen in the API layer, not in the component layer, as the error handling should include showing a generalized error message to ensure security.

#What should have been the approach?

Even if the backend finds that we have no entities matching the filters that the frontend wants, it is still a valid request. So the backend should have sent a 200 status code (on subsequent requests it might be automatically converted to 304).
